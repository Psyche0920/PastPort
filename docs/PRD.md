## 1. 产品是什么，要证明什么

PastPort 将真实 vakıf 遗产资料转化为照片观察、证据推理、人物互动与有后果的选择，并提供可审核、可编辑、可复用的制作系统。玩家通过行动理解建筑与遗物的用途、服务对象和社会关系；运营方可以持续添加内容并追踪依据。

首期须证明：**同一套制作流程与游戏底座，可以将两个不同的官方资料项目做成可玩的内容；第二个项目主要增加资料和内容包，不复制游戏代码。**

| 用户 | 需要解决的问题 | P0 提供什么 |
|---|---|---|
| 线上玩家、未来游客 | 看得懂目标，能观察、判断和选择，形成真实空间认识 | 无需到现场的 2D 游戏、照片线索、人物后果、来源入口与本地存档 |
| 内容编辑 / Matt | 资料如何变成有趣且自洽的任务 | 情节 Skill、结构化故事、人工修改与锁定、预览和试玩反馈 |
| 研究审核者 / Weng | 哪些信息可采用，依据和许可在哪里 | 来源索引、主张与图片审核、冲突和缺口、版本化证据包 |
| 系统整合者 / Weijia | 如何自动推进、控制费用、发布并复用 | 有限循环工作流、状态恢复、统一契约、装配发布与运行报告 |

成功必须同时满足：历史依据可追溯、照片实际参与玩法、任务推动人物目标、选择产生后续影响、路线空间连贯、第二项目可复用。模型自评或程序通过均不能代替真人体验验证。

### 1.1 先验证体验，再扩大制作能力

首个交付单位是短样段：一条经审核的遗产信息前提、一次依赖该前提的判断、一个有代价的人物选择、一处可见的后续变化，以及可追溯的制作记录。先验证玩家能否说清“依据是什么、为什么这样判断、选择改变了什么”，再扩大章节规模和编辑后台。小样段失败时优先调整材料、玩法和人物动机；不通过增加模型、表单或流程节点抵消体验失败。

产品验证分两条记录：玩家体验验证，以及制作效率验证。工程依赖允许并行推进，但不能用工作流完成率替代玩家体验结果。消费端付费产品、机构制作服务或二者结合的商业定位仍待团队确认；本次修订不预设付费意愿或机构采购成立。

| 验证对象 | 首期观察与记录 | 不代表什么 |
|---|---|---|
| 玩家体验 | 无主持人代操作的完成情况、遗产依据/选择后果的原话、卡点、想继续的原因 | 小样本不证明市场规模或统计显著性 |
| 制作效率 | 首次可玩耗时、人工审核/修改分钟、返工次数、被修改场景数、实际外部费用 | 模型输出结构合法不等于节省人工 |
| 跨项目复用 | 第二项目与首项目的差异、复用模块、必要扩展、额外人工工作 | 只换名称和照片不证明玩法适应性 |

真实材料、真实模型和真人试玩分别留证；合成 fixture 只验证工程合同。未知费用/时间写 unknown，尚未运行写 not_run。字段统一见 Workflow，不再建立一套独立评分系统。

## 2. 游戏单位与官方资料如何对应

### 2.1 默认划分

**一个官方同层级资料文件夹，默认对应一个游戏项目。** 项目保留该文件夹的全部已登记资料和现实地点清单；玩家体验在项目内部拆成章节与连续路线。官方文件目录是当前可见的资料组织方式，尚未获得官方数据库表结构。

| 层级 | 含义与边界 | 系统对象 |
|---|---|---|
| 官方资料集合 | 保留实际提供的城市、行政区、出版卷册层级，不凭名称重建不存在的层级 | `SourceCollection` |
| 官方文件夹 | 同级的具体建筑群或专题材料目录，是项目默认来源边界 | `SourceFolder` |
| 游戏项目 | 负责该文件夹的材料覆盖、选点取舍与内容制作；不等于一条路线 | `GameProject` |
| 现实遗址 / 建筑 | 有可核验身份和位置的地点实体；同一实体可出现在多个专题中 | `Site` / `Building` |
| 路线与章节 | 项目内一组连续探索地点及其对应故事；一个项目可有多条路线和章节 | `Route` / `Chapter` |
| 场景与任务 | 玩家在具体地点进行的观察、对话、推理或选择；同一地点可有多个场景 | `Scene` / `Task` |

当前 Drive 入口为 [I. ve II. Cilt - Osmangazi](https://drive.google.com/drive/folders/1JKfRtUyYACkqpVLhLeMsWE0kA2mdSNQ1)。目录表记录了 15 个一级文件夹，内部文件清单抽样核实了 8 个。具体目录见 [Excel 说明表](../references/source-directory.xlsx)。文件大小和目录形态只说明材料规模，不能据此认定每个文件夹都已足够支撑完整游戏。

- **具体建筑群 / 遗址文件夹**：如 II. Murat、Hamzabey，优先作为一项目一组现实相邻地点的候选。
- **专题文件夹**：如教育建筑、清真寺与墓园，仍对应一个制作项目；先拆清实际地点，再组织项目内路线。不能把同一专题中分散的地点硬串成一次连续游览。
- 默认一文件夹一项目，确需拆分或合并须记录范围、来源映射、原因和审核人；不静默改变制作边界。
- 地点全集逐项标记主线、支线、后续路线或不纳入，并记录理由；具体枚举统一见 [Workflow 数据合同](WORKFLOW.md#3-数据边界与三个包)。未进首条主线不等于从资料库删除，也不宣称全部地点已可玩。

### 2.2 稳定标识与资料更新

`source_folder_id` 使用平台稳定文件夹标识及来源命名空间，不能仅用名称或可变路径。保留原名、原路径、父目录与采集时间；同名目录不自动合并，重命名不产生新项目。`project_id` 为内部稳定 ID，与来源通过显式映射关联；多个文件夹出现同一建筑时引用同一 `site_id`，来源证据分别保留。

导入按文件 ID、hash 与解析版本识别新增、修改、重复和失效。更新只进入作者态，并列出受影响的证据、章节和资源；既有发布快照保持可运行。源文件更新、被移除或授权变化均触发影响检查，不能自动沿用旧审批。已发布资产确认失去使用资格时，运营须停用相关版本或回滚至获准版本，而非继续分发旧包。

### 2.3 空间顺序是制作约束

P0 就要模拟游客的连续探索体验，**从资料筛选和情节设计开始落实相邻、可通行、少折返**，无需等待 GPS 或 P1 的动态路线规划。

先确认项目范围与地点清单，再形成有依据的连续地点序列，围绕这条序列筛证据、选视角、写情节。候选故事可以促使调整路线，但调整后必须重新核对空间；不得为了顺路编造历史联系。

每条路线记录起终点、有序 `site_id/building_id`、段落通行依据、距离/时间来源及更新时间。坐标接近不等于道路连通；核对实际步行路径、入口、围墙、可访问区域或可靠场地图。无依据的精确距离和时间保持未知。物理访问条件与线上可玩状态分开。

主线不得要求跨越不相邻节点或反复往返取物。不可避免的支路往返须展示原因并经人工确认；分散地点拆为项目内不同路线。地图与照片只能支持示意时明确标注，不能声称已复原真实游览路径。距离、时长阈值待 Bursa 样本核验后确定，不预设任意公里数。

## 3. 首期范围与现有基线

| 阶段 | 交付 | 暂不纳入 |
|---|---|---|
| P0 | Muradiye 抽象与兼容参考；证据与叙事流程；四模块契约；最小审核编辑发布工作台；固定连续探索顺序；第二项目可玩复用；中英规则一致 | 城市动态 Planning、GPS 到访解锁、精确室内 3D、多人玩法、公开 SDK、开放式玩家聊天 |
| P1 | 3–5 个合格项目/内容包、2D 城市地图、按时间/兴趣/进度推荐与重规划 | 无依据的交通时间和现实到访保证 |
| P2 | 经核验的地理服务、可选 GPS、证据分级的 3D、外部 API/SDK 评估 | 将 AI 补齐几何宣称为测绘复原 |

现有 Demo 对应 **Muradiye 建筑群内的一章五场景故事**，尚非整个 Osmangazi 或完整官方目录的游戏。第二项目优先从同层级的另一具体建筑群文件夹选择，不用 Muradiye 内两个节点冒充跨项目复用。建议最小验证为三个场景、两种任务和一次有后续效果的选择；具体对象与规模待资料评估冻结。跨城市目前是设计目标，需另行实跑才可宣称已验证。

第二项目在资料、许可和空间可行性通过后，应至少在核心推理依据、任务组合、角色目标或结果维度之一明显不同于 Muradiye；差异必须来自材料。允许有依据地增加通用 Handler，记录扩展原因与回归影响；不得为了证明零改引擎把新故事强塞进运货/账单模板，也不为“不同”编造历史特点。

当前仓库状态：`main` 已实现 T1a 共享合同、模块 Protocol、Schema 和隔离契约样例，见 [合同交接](CONTRACTS.md)；尚无生产框架服务、LangGraph 制作服务或新通用播放器。Muradiye 的可玩代码、数据、媒体及原回归测试完整保留在 [demo-muradiye 分支](https://github.com/Psyche0920/PastPort/tree/demo-muradiye)；不计作 main 的已实现能力。主分支只保留抽象方法、校准范例及引用，后续通过小型获准 fixtures 验证兼容，不复制整套 Demo。

当前本地 CI 配置已增加 T1a 类型、格式、Schema/样例与离线契约测试，远端生效仍需推送后核验。Demo 测试不作为 main 结果；流程恢复、真实双项目和浏览器验收仍待后续任务，不能把合同检查通过称为工作流已实现。

## 4. 玩家体验与内容标准

主循环：**角色处境与目标 → 观察照片/资料 → 获得线索与判断 → 行动或选择 → 人物/公共服务后果 → 保存进度并解锁下一场景。** 首屏交代我是谁、出了什么问题、现在做什么；背景和出处按需展开。

关键推理任务须让玩家表达判断，例如选取支持材料、比较解释或排除假设；不强制自由文本。解题前提供必要前提，错误反馈帮助定位缺失观察。关键选择同时呈现可理解的收益/代价、即时人物反应及后续可见状态。定位点击、过场和气氛描写可以存在，但不单独计作核心遗产推理；移除/替换依据测试与真人观察按 Workflow §18 执行。

| 设计对象 | 必须满足 |
|---|---|
| 主线任务 | 同时关联遗产属性、人物目标及完成/拒绝后的影响；答案能由已到达场景的材料推得 |
| 真实照片 | 可观察细节实际参与解题，支持放大和明确反馈；不能只是背景装饰。现代陈设不作为古代事件/用途的证明 |
| 人物成长 | 至少出现一次可见的前后行为变化；由任务、关系或职责状态支撑 |
| 重大选择 | 改变后续证据、人物协作、权限、支线或服务结局；不能仅替换末尾评价 |
| 历史表达 | 史实、解释性推断、原创虚构明确区分；虚构账目/数量/证词和真实人物戏剧化台词不伪装为原件 |
| 任务形式 | P0 支持观察、照片热点、分类/匹配、证据组合与选择；按材料选用，不强迫每个项目凑齐类型 |
| 交互与提示 | 每次操作有明确结果；错误提示指出缺少的观察，不悄悄改变答案；故事时间与实际耗时分别记录 |
| 语言与可访问性 | 中英共用 ID、规则、答案和后果；键盘操作、文字观察替代、非纯颜色反馈；替代文本提供同等信息而非直接答案 |

Muradiye 既有故事按“抵达账目—庭院担保—喷泉证人—食堂分类—核对签署”复审。真实服务背景与照片构件须有依据；虚构数量、货运差错和证言保留清楚标记。帮助证人应影响可得证明，承担/掩盖/转嫁责任应影响人物与服务，不因旧故事已存在而反向只找支持证据。

页面覆盖入口、场景、笔记/证据板、来源抽屉、结局反馈、存档恢复与重开。缺图时提供经审核的等效观察方式，否则停用受影响版本；证据未获得不能用于提交。存档版本不兼容须告知，不静默清空。首次玩法不可用时显示资料说明，不伪装可玩。移动端按 360–430 CSS px 验证，触控目标建议至少 44×44 CSS px，无强制真实倒计时。

## 5. 四模块架构与交接

```mermaid
flowchart LR
  Source[官方目录与原始资料] --> Evidence[1 资料与证据模块]
  Evidence -->|已审核证据快照| Story[2 情节模块]
  Story -->|结构化缺口请求| Evidence
  Story -->|已终审故事包| Assembly[3 装配与发布]
  Evidence -->|绑定版本及许可记录| Assembly
  Assembly -->|标准运行内容包| Engine[4 通用游戏底座]
  Engine --> Player[玩家操作与独立存档]
```

| 模块 / 主责 | 接收与产出 | 完成边界 |
|---|---|---|
| 资料与证据 / Weng | 原始资料与研究问题 → 索引、支持/反证、图片/区域映射、位置/通行依据、许可及审批组成 `EvidencePackage` | 供故事使用的关键史实、争议和解题证据已逐项人工审核；不明项明确不可用；锁定版本/hash |
| 情节 / Matt | 已审核证据、空间序列、体验目标 → 人物、场景、对白、任务、线索、条件/效果、语言组成 `NarrativePackage` | 人工内容终审完成；历史表述和解题有依据，因果闭合；缺口回资料模块，不自行认证事实 |
| 装配发布 / Weijia | 两份已定稿包及审批记录 → 确定性映射、机械构建报告、不可变 `RuntimePackage` 与发布记录 | 校验格式、版本、引用、批准状态、资源、规则和语言完整性；失败定位退回；不重判史实或改写剧情 |
| 通用底座 / Matt，Weijia 集成 | 运行包与存档 → 照片场景、任务、选择、进度、后果 | 同一底座运行不同项目；玩家动作不调用 LLM；不修改已发布内容 |

四块是逻辑模块，P0 用一个 Python 后端部署即可。工作台经 API 调用制作/审核/发布用例；LangGraph 保存流程 checkpoint，业务库保存审批权威记录，二者不能互相冒充。来源、作者态、运行包和存档各有清晰边界。

P0 采用模块化单体：证据服务、叙事服务、执行记录/费用账本、审核服务与发布服务通过应用用例协作；工作流节点只调度这些用例。玩家读取不可变发布包，制作服务停机不应使已加载的游戏动作依赖模型。共享身份、预算、审批和恢复逻辑集中维护，不在各节点复制。当前规模不拆微服务，不为四个逻辑模块建设四套部署系统。

### 5.1 内容契约

| 契约 | 核心内容 | 版本关系 |
|---|---|---|
| `EvidencePackage` | 项目范围、地点、主张、来源、图片、许可及空间依据 | 引用的关键内容逐项批准；来源与审核可追溯，快照不可覆盖 |
| `NarrativePackage` | 人物、路线、场景、任务、选择、后果、语言与事实/虚构引用 | 绑定具体证据快照；修改后重新终审，不能引用其他项目的不可用素材 |
| `RuntimePackage` | 可由通用底座解释的玩法、合法资源及完整性清单 | 由装配器确定性生成并绑定依赖；发布后不可覆盖 |
| `PlayerState` | 当前场景、观察、物件、选择和后果 | 固定到项目与发布版本；显式迁移或继续旧包，无跨项目串档 |

一个项目可含多个地点；不能把单点范围当作整个项目。参考数据映射必须显式保留原始证据身份，格式兼容与内容发布分版本管理。精确字段、枚举和版本关系唯一维护在 [Workflow §3](WORKFLOW.md#3-数据边界与三个包)，玩家状态在 [§9](WORKFLOW.md#9-通用玩法合同与一个真实映射例)；本节只定义业务责任，不另列一套 Schema。

主线任务须有目标、遗产依据、可获得的线索、答案规则、人物关联、状态后果、反馈、提示与无障碍替代；视觉任务须有图片及区域依据。字段与类型按 Workflow 合同实现。场景明确关联现实地点或标注非空间过场，不能用过场掩盖跳跃路线。

底座只解释有限原语，例如 `has_evidence / observed_all / choice_equals / grant_item / set_relationship / add_story_time / unlock_scene`。每种条件、效果与任务 Handler 有 Schema、解释器和测试；禁止内容嵌入脚本、`eval` 或 `if site_id == ...` 专用分支。新玩法扩展为可复用 Handler，不要求完全不同的玩法零改引擎。

装配器机械检查包含：Schema 与引擎兼容；ID/语言键完整；引用审批快照匹配；许可范围满足当前分发；资源存在且 hash 一致；规则可解释；场景可达和线索条件可满足。复杂状态下的通关由规则路径测试验证，不能以一项静态检查宣称全路径无死锁。

## 6. AI 制作工作流

**起点属于资料模块；首个 LLM 角色由资料是否已可用决定。** 一个文件夹只确定来源边界，不代表已形成可供创作的证据数据库。先用程序建立有出处的轻量索引，再让 Story Agent 从材料里发现方向，Database Agent 随后围绕选中的方向研究。避免先全量深度研究，消耗大量费用却没有可玩的叙事机会。

| 输入状态 | 从哪里开始 | 进入下一步的条件 |
|---|---|---|
| 只有文件夹/PDF/图片 | 资料模块：Python 清点、去重、解析和定位；复杂史料理解、实体映射按需调用 Database Agent | 文件身份、相关片段、候选地点与图片状态可查；失败与未知明确标记 |
| 已有可用轻量索引，尚无故事方向 | Story Agent 的 Discovery，再由 Database Agent 定向研究 | Discovery 仅产候选与问题；未审核主张不能直接进入正式叙事 |
| 索引不足以形成方向，但有范围内可定位缺口 | 资料模块先针对缺口补证，再返回 Discovery；无需先选一个故事 | 与定向研究共用轮数/预算；新增事实仍是候选，不能跳过审核 |
| 已有与当前来源 hash 一致、适用范围匹配且审核有效的 EvidencePackage | 直接进入 Story Agent；没有方向则先 Discovery，有已选方向则正式生成 | 程序检查证据/许可/空间记录与审批状态；发现新增问题再提交研究请求 |

首次 LLM 调用可以发生在资料模块的复杂抽取，也可以在程序成功解析后直接进入 Discovery；不能为了“Database Agent 必须先运行”额外增加无必要调用。资料、情节相互反馈，但所有正式事实仍须经过资料模块审核。

| 步骤 | 自动工作与产物 | 人工介入 / 负责方 |
|---|---|---|
| 1 建项目、登记与轻量索引 | 资料模块优先用 Python 处理文件身份、去重与定位；Database Agent 只处理需要语义判断的抽取/映射；列出地点、空间与素材缺口 | Weng 确认范围、实体与可用性；Weijia 提供导入状态 |
| 2 Discovery | 基于有出处片段与可行空间序列，提出 2–3 个视角、证据、未知问题及互动可能 | Matt 定探索标准；方向是假设，不能当定稿史实 |
| 3 筛选与定向研究 | 先列证据、缺口、玩家行为、人工工作和推荐理由；方向确认后定向找支持与反证、核图像/地点 | Matt 在首期确认方向；Weng 确认资料硬边界；模型评分仅作建议 |
| 4 证据审核 | 汇总到具体版本的来源、冲突、许可和所选路线/通行依据 | 关键史实、争议、解题证据和路线在同一关口逐项决定；通过后交付批准证据及路线，不新增审核阶段 |
| 5 正式生成与打磨 | 基于批准证据生成/修改故事、任务和后果；保留人工锁定字段 | Matt 预览、修订与内容终审；涉及新史实返回步骤 3–4 |
| 6 装配与发布 | 按第 5 节转换、校验、打包，原子切换发布版本 | Weng/Matt 完成领域审核；Weijia 执行发布，可回滚 |

资料审核 Skill 与情节 Skill 分别由 Weng、Matt 维护。ResearchRole、StoryRole 共用 `ModelGateway`，按阶段隔离上下文、工具权限和输出模型；可共用模型或 Agent 实例。LangGraph/Python 负责执行与状态，不另加一个 LLM 总控，不做自由协商式多 Agent。独立模型审校仅在实测证明价值后按需增加，不能替代人审。

研究角色可以作出 `supported / qualified / conflicting / insufficient` 判断并交出依据，但批准权归人。Discovery 可读标有状态的索引；正式生成只使用允许范围内的审批快照。Skill 是专业操作规范，不能代替程序权限控制。

两套初始项目 Skill 和 Muradiye 校准范例见 [Evidence](../skills/evidence-review/SKILL.md) / [Narrative](../skills/narrative/SKILL.md)；遗产系统与开源方法源头、许可和采用决定见[参考评估](REFERENCES.md)。它们尚待运行时接入与真实效果评测。关键任务须说明遗产信息如何改变玩家推理及人物后果，不能仅用“点照片领取虚构线索”满足要求。Workflow 骨架后先做真实可玩样段，再扩大后台与章节生产。

### 6.1 有限循环与人工优先

- 每个 run 的范围补证与定向研究合计最多两轮；研究轮内的工具调用也受预算限制。无方向可以按具体缺口补证，选出方向后不重新计数；换候选不偷偷清零。
- 自动叙事修改最多两轮，达到上限交给人。格式修复建议最多一次；不能借格式修复继续研究或改剧情。研究与叙事计数独立。
- 每个 run 必填调用数、input/output tokens、搜索/抓取数、输出长度、活动截止时间和现金上限。首次付费试跑先由执行人设限，长期阈值依实测确定；无预算不付费运行。
- 资料不足、无进展、冲突、授权不明、预算耗尽分别记录原因；可缩小范围、退回或放弃方向，不用模型常识补成史实。大幅改题新建有预算记录的版本/run。
- 合格候选按 **人工锁定 > AI > 审核过的 fallback** 选用；全部不合格就阻止发布。AI 不覆盖锁定字段；人工改答案、来源或关键主张同样要重新审核。

轮数约束自动化范围，不证明研究充分；首期两轮上限保持有效。每个问题记录足够支持、冲突、不可获取、无进展或预算不足等停止理由。达到轮数上限先由人处理现有成果；若需增加自动研究，须事先修改版本化政策并经明确授权迁移 run、记录新上限和追加预算，未实现该流程时拒绝额外调用。不能通过 resume、扩大问题集合或新建 run 隐藏累计消耗。

### 6.2 状态、恢复与工作台

完整制作流程：登记与索引 → Discovery/方向选择 → 定向研究 → 资料审核 → 生成与修订 → 故事终审 → 装配校验 → 发布确认 → 发布。工程上用独立的 `node + status` 表示阶段与运行/等待状态，精确枚举及路由统一见 [Workflow 实现合同 §4](WORKFLOW.md#4-图状态节点与路由)。复用已验证索引或证据包时记录复用快照、入口校验及跳过原因，不能仅改状态字段绕过前置条件。修改反馈回所属阶段。

每次迁移保存输入/输出版本、操作者、原因和累计耗用。审批绑定具体 hash；证据变更使相关故事审批失效。恢复依赖持久 checkpoint，业务服务再核审批与预算；外部副作用使用幂等键，远端响应未知时先核对/标记待处理，不盲目重试导致重复付费。人工等待与活动计算时间分开统计。

恢复默认从失败节点内未完成的小步骤继续，复用输入版本和依赖仍有效的已完成产物；禁止因局部失败默认重跑整个项目。资料/反馈变更仅使关联证据、章节及后续审批/校验失效，预算和轮次不清零。具体恢复、缓存和故障验收见[Workflow 恢复规范](WORKFLOW.md#6-重试局部返工和-token-账本)。

工作台与 API 必须覆盖：项目/目录导入状态、run 创建查看取消、来源与主张/图片审核、候选与研究缺口、人工任务编辑与锁定、预览、批准、校验、发布回滚、玩家公开包读取及自愿反馈。草稿不走玩家公开接口。错误提示保留具体原因，不以虚假内容或通用成功提示替代故障。

首版界面围绕决定组织：原文与主张对照、候选比较、故事/状态预览、修改影响和发布阻塞。优先支持从合法动作路径进入目标场景、对照两个选择、查看规则触发及后续读取位置。调试状态仅用于内部预览，不作为玩家正式存档或审核通过的证据；具体边界见 Workflow §8。

## 7. 数据治理与技术路线

### 7.1 数据职责

| 对象 | 必须保留 |
|---|---|
| 来源 / 片段 | 文件身份、URL/路径、hash、作者/出版信息、获取时间、页索引与印刷页、段落/区域、解析版本；访问日期不是出版日期 |
| 历史主张 / 证据链接 | 主张文本、地点/实体/时间范围、原文定位、支持与反证、来源类型、证据判断与人工结论；转载不算独立证据 |
| 图片 / 衍生物 | 原图与衍生图 hash、建筑/细部映射、可见区域、图注、所示时间、许可依据与允许用途、审核人；禁止用现代细节证明古代情节 |
| 空间记录 | 地点身份、坐标/入口/通行关系、资料出处、核验状态与日期；行政归类、实际路由与剧情次序分开存 |
| 审核 / 版本 | 审核对象 ID/version/hash、决定、理由、操作者和时间；源文与既有审批不被生成内容覆盖 |
| 运行 / 反馈 | 制作阶段、累计预算、产物版本、失败和重试；玩家反馈只收集必要且自愿的信息，不默认记录精确位置或身份 |

来源顺序：官方 Drive 与出版物先登记索引；有界补充官方文化机构、遗产管理机构和学术来源。博客/聚合页只作寻源线索，不能独立支撑关键史实。源文件状态区分 `discovered / downloaded / parsed / failed`；大文件未获取、OCR 失败和图片未映射必须可见。

当现有资料不足以支撑故事时，允许按明确缺口主动联网研究权威来源，再按同一证据流程审核入库。外部参考资料单列来源登记表，记录机构/作者、URL、原文定位、对应缺口/主张、支持/反证、许可、筛选状态及理由；区分官方提供与外部补充。具体来源清单逐项筛选后配置，建议类别及字段见[外部来源登记](REFERENCES.md#6-外部来源登记与补证边界)。

证据判断、人工审批、照片映射、内容性质、许可和索引质量独立：分别使用 `supported/qualified/conflicting/insufficient`、`pending/approved/changes_requested/rejected`、`unmapped/provisional/verified`、`historical_fact/interpretation/original_fiction`、`unknown/restricted/permitted_for_scope/open_license`、`extracted/needs_ocr/checked/failed`。官方提供不自动等于可再分发；缺许可或身份的图片不作为发布资产/指定答案。旧 approved/verified 标签只有存在对应审批证据才继承。

**作者态数据库是编辑真相，版本化运行包是玩家读取真相。** 迁移前备份并记录 hash，扫描旧引用与审核依据，导入并标记 legacy，比较旧章节分支结果后切换。`--replace` 仅用于明确可重建的派生库，不能覆盖正式审批库。审批日志与 checkpoint 均不等于备份，需独立恢复验证。

编辑产生变更影响报告，区分事实、解题规则、人物因果、翻译、媒体呈现和许可变动。未变条目的有效审批可复用；新故事/运行包仍绑定新版本和所需整体终审。系统可以计算受影响范围，不能仅因文件差异小就自行批准内容。

停用发布版本应阻止后续在线分发，并在客户端再次联网核验时提示停用。已下载的副本无法保证被远程即时收回。P0 不承诺完整离线分发或离线状态下即时撤回；媒体许可范围须覆盖实际缓存/下载方式，未来增加离线支持前另定再核验及过期政策。

### 7.2 技术基线与部署约束

| 层 | P0 选择与限制 |
|---|---|
| 编排与模型 | LangGraph/Python + 统一 ModelGateway；不强制叠加 PydanticAI/LangChain；不以 Jeff/JEV 替代历史语义判断 |
| 后端 / 契约 | FastAPI；Pydantic 2、不可变 dataclass、Protocol/ABC 为实现基线；Python 3.12 建议值，依赖兼容确认后锁定 |
| 存储 / 检索 | SQLite + 独立管理的持久 checkpoint；单应用实例起步；元数据/FTS 关键词检索；P0 不搭向量库 |
| 前端 / 运行 | 原生 HTML/CSS/JS；共享解释器/渲染器、独立语言资源；玩家只加载本地/静态获准内容，无 LLM 等待 |
| 发布 / 部署 | 不可变包、JSON manifest、hash、原子发布与回滚；本地优先，公开时落实认证、HTTPS、持久存储和备份 |
| 数据访问 | 标准库 SQLite Repository 与顺序编号 SQL migration；P0 不引入 ORM，迁移可测试、可恢复，具体合同见 Workflow |

后端、通用玩家端、专业 Skill 与测试按职责分开；具体拟建路径和依赖边界统一见 [Workflow §12](WORKFLOW.md#12-code-agent-实施任务与验收)。领域层不依赖 Web 框架、编排器或供应商 SDK。Coding Agent、代码质量与 CI 规则见[工程规范](ENGINEERING.md)。

首期工程基线与逐项任务见 [Workflow 实现合同](WORKFLOW.md)：冻结包/节点协议、保存恢复、账本和通用玩法；Weng/Matt 通过版本化政策与 Skill 调整专业方法。规范中的流程是目标行为，完成状态以代码和验证记录为准。

模型选型比较 2–3 个候选，用相同证据集与 Skill 测抽取定位、冲突/不足、图片未知、叙事机会、任务因果和局部改稿。建议至少 12 个案例，关键生成重复测稳定性；Weng/Matt 盲评，Weijia 记录版本、成功率、费用、人工修改分钟及 p50/p95 延迟。质量达标后选每个可交付包综合成本最低者，不写死供应商或“最优模型”。

`cost_per_accepted_package = total_measured_external_cost / accepted_packages`；零合格包报告无可用产出。现金费用与人工分钟分别列出。按 hash、Skill/Schema/模型配置和审核快照缓存；只传相关片段、摘要和 ID。调用失败保留状态并显示真实原因，未经确认不静默换模型。

制作效率同时记录首次可玩耗时、审核/修改的人工分钟、返工次数与影响范围；保留人工基线、AI 初稿和最终稿，不只比较 token 单价。与基线相比只有质量不下降且可观察制作负担降低时，才扩大自动化；目标阈值由首次样段数据校准，不虚构节省比例。

### 13.3 产品验证顺序和暂停扩张条件

本节约束产品内容验证与扩大投入，不作为搭建共享合同、Workflow、模块接口及隔离 fixture 的前置门禁；框架开工按 §13.5。两条工作线可并行，不能把真实内容未完成当成接口无法开发的理由。

1. **冻结一个试验简报**：目标人群、材料范围、关键推理、选择/后果、主要语言、观察问题、允许使用范围；商业定位未定不阻塞内部体验学习，但阻塞宣称商业价值。
2. **先验证设计样段**：少量可定位材料、人工审阅和可展示的分镜/交互即可用于内部设计观察。未知史实不能作为确定答案，未知路线明确标注；这类结果不计作 T5a 自动生成或正式发布验收。
3. **进入已授权的工程与真实制作任务**：按 Workflow T1a→样段必要 T2/T3/T4/T6→T5a 推进；T5a 对真实调用、审批和恢复的要求不因设计样段已展示而省略。
4. **仅在质量与负担可接受时扩完整后台/章节**：关键推理不成立、玩家无法解释选择后果或人工返工增加时，先修原因。未验证改善不得用“架构已经支持”替代结果。
5. **第二项目验证方法适应性，再完成交付**：分别报告内容差异、引擎扩展、人工工作和真实试玩；原项目的工程检查不自动批准新项目内容。

每轮只处理观察到的失败及其依赖闭包。预算/研究上限到达后按原政策停止并交人决定；连续没有新增有效材料或可观察改善时，选择缩小故事、换可用方向或停止当前候选，不能默认增加 Agent、上下文或工具调用。具体阈值在试验开始前冻结，保留合理不确定性，不事后改门槛使结果通过。

### 13.5 框架是否足以开工：以模块独立优化为目标

**结论：现有架构足以启动合同与骨架建设；尚不能宣称模块接口已搭好，也不能直接让各人按自己的理解自由实现。** 当前已有模块职责、三包、状态/审核/预算/恢复设计；仍需将文字落成一套共享类型、可调用接口、依赖注入、适配器和独立验收样例。完成这些是第一阶段框架交付，不必等待故事最终质量、真实模型选型或第二遗址资料齐备。用户随后已授权 T1a，合同层已实现；其余编码仍按用户授权任务开展。

之前“先验证样段再扩大平台”的要求保留在产品线：限制完整后台、全量研究和内容量。它不阻塞框架线实现所有首期模块的最小接口及 Workflow 连接；每个模块先支持一条真实可执行的 fixture 路径，后续提升模块内部质量。

| 当前容易误判之处 | 开工要求 | 后续可独立优化的部分 |
|---|---|---|
| 有三个包就等于有接口 | 包是产物；还须有入口操作、输入/输出、错误/取消、持久化责任与兼容政策 | 模块内部研究、生成和装配算法 |
| Skill 是模块实现 | Skill 是专业政策；运行时还须有受控调用适配器、类型验证和依赖注入 | Weng/Matt 修改 Skill、样例与专业策略；变更留版本 |
| 图节点是业务服务 | 节点只调用应用用例并选择合法路由；业务权限、账本和写入集中执行 | 调整单个模块内部步骤，无须改全图 |
| fixture 跑通就说明模块可用 | fixture 只证明连接/状态/隔离和错误传播；真实模型和故事质量另验 | 在相同合同下逐一替换真实适配器 |
| 三人各建自己的 DTO 和数据库接口 | 共享契约唯一维护，模块只通过声明的接口访问权威数据 | 内部数据结构可不同，出边界必须转换验证 |
| 通用等于任何玩法无需引擎改动 | 冻结有限能力和版本；新增玩法走通用 Handler 扩展 | 新任务类型不硬编码地点；旧包继续通过兼容验收 |

框架第一交付应证明：**同一份 Workflow 可以组合测试资料模块、测试叙事模块、真实确定性装配/运行核心；替换其中一个模块不要求修改其他模块内部代码。** 测试审批仅限隔离测试环境，测试产物不得进入公共发布。正式审核和预算判断不能为演示连通而改为恒真。

内容专业负责人决定内容质量，框架负责人保证机制。任何模块均不能直接修改其他模块作者态、图 checkpoint、批准结果或发布指针；对外反馈用类型化结果/缺口请求，不能靠私下调用对方内部方法完成流程。

框架完成至少满足以下要求，逐项留证后才允许称“接口搭好、可分工优化”：

1. 共享合同可执行：首期每个模块入口有类型、Schema、完整有效/无效样例和已冻结兼容规则；各方使用同一版本。
2. 可独立运行模块：每人通过本模块的固定输入 fixture 和契约验收入口开发，不依赖其他模块正在运行或已经连接真实模型。
3. 可装配完整流程：通过依赖注入替换资料/叙事适配器；登记、索引、候选/方向确认、研究、证据审核、叙事、终审、装配、校验和隔离发布全程可达。界面只需支撑查看与必要决定，不要求完整后台。
4. 失败真实可控：至少证明缺口退回、审核过期、预算不足、取消、成功步骤恢复不重复、非法输出拒绝与跨项目隔离；不能只有成功演示路径。
5. 运行与制作分离：发布包驱动共享运行器，游戏动作不调用制作模型；至少一项选择改变后续可见状态，且刷新恢复仍一致。
6. 交接可复现：README 有确切启动/检查入口、版本与环境配置，模块替换示例、已支持/未支持能力及负责人；缺凭据时标未配置，不自动切成假成功。

真人试玩、第二真实项目、生产授权和成本优化属于框架之后或并行的质量验证，不能据框架通过一并宣称完成。接口的具体操作与调用约束唯一维护在 Workflow §19。

T1a 交付记录：共享合同基线 0.1.0、模块 Protocol、可复现 Schema 与合成正反样例已形成；技术检查结果见 [合同交接](CONTRACTS.md)。团队专业确认、实际 Workflow 连接及玩家执行仍分别验收，不能把本条当作 §13.6 的整体框架完成证明。
